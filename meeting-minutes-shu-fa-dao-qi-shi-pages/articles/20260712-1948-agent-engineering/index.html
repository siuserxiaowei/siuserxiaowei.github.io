1. 执行摘要：这场会真正讲了什么

这不是一场单纯的工具推荐会。三位嘉宾分别补齐了 AI 产品从“做出来”到“做成”再到“被理解和传播”的三段系统。

  → 明确用户心智与产品禁区

  → 用模型评测和真实用户验证
  → 用设计系统保持一致

1.3. 十个最重要结论

  1. 从真实痛点出发，比从热门技术出发更容易做出有用产品。
  2. 先选最轻的产品形态：快捷方式、油猴、插件、网站、完整产品逐级升级。
  3. AI 让功能和 Demo 变便宜，也让单一创意更容易被复制。
  4. Skill 的核心是把可靠的单步能力串成完整任务，但生产级还需要权限、状态、错误、验收和版本。
  5. 模型没有脱离场景的“最好”；质量、成本、延迟、稳定性和输出介质必须一起评估。
  6. 产品定位决定用户怎么理解你、拿你和谁比较；功能再强也不能破坏核心心智。
  7. 获客、留存、付费可以由不同角色参与，但必须属于同一价值链。
  8. Design System 的价值不是“好看”，而是让网页、PPT、视频和团队成员长期说同一种品牌语言。
  9. 开源、BYOK、免费、本地优先不是同义词；控制权、成本、隐私和治理要分开分析。
  10. Agent 可以执行，但责任不能委托。VPS、密钥、浏览器、发布、版权、陪伴关系都需要明确边界。

2. 乔向阳：从真实摩擦到个人软件工厂

2.1. 核心命题

乔向阳并非传统研发背景。他自述做过网站和创业，在字节工作六年，最后一段经历与 TikTok 商业化 AI 产品相关；他强调自己长期是产品经理、只懂少量 HTML，却在一周内做出多个项目。这段分享真正说明的不是“不会代码也能一键做 App”，而是：当代码生成、浏览器操作和计算机操作被 Agent 接起来后，人的稀缺能力转向问题定义、工作流设计、方向选择、验收和复盘。

2.2. AI Coding 演进：不要把四个词误写成四代产品

乔向阳把个人感受描述为：Chat 对话复制代码 → Vibe Coding → Spec Coding → Loop Engineering / Harness。

更准确的关系是：

  • Vibe Coding：一种自然语言驱动、快速试做的人机协作风格。
  • Spec-driven Development：用规格、约束和验收固定“到底做成什么”。
  • Agent Loop / ReAct：模型观察、行动、读取结果、继续判断的执行循环。
  • Harness：承载上下文、工具、权限、状态、重试、预算、追踪、评测和恢复的工程系统。

它们不是严格线性替代，可以同时存在：用 Vibe 探索，用 Spec 固化，用 Loop 执行，用 Harness 保证真实世界中的可靠性。

2.3. 为什么从 Claude Code 转向 Codex

他的理由不是一句“代码能力更强”，而是 Browser Use 与 Computer Use 让开发—测试—操作真实界面的链路更顺。

可迁移判断：选择 Coding Agent 时至少比较：

  1. 写代码；
  2. 读项目与文档；
  3. 运行测试；
  4. 浏览器验证；
  5. 操作本地应用；
  6. 权限与审批；
  7. 长任务恢复；
  8. 结果可追踪性。

2.4. 案例卡 Q1：公众号后台配图按钮

  • 时间：00:25:29–00:26:50。
  • 痛点：公众号文章需要配图，要反复复制关键词、切换到即梦、粘贴并生成。
  • 做法：给公众号后台增加按钮，自动提取/复制关键词，跳到生图工具并粘贴，使用固定个人风格生成封面。
  • 价值：没有重新造一个生图平台，只消除了现有工作流中的连接摩擦。
  • 依赖：浏览器脚本/扩展、稳定 DOM、剪贴板和跳转权限。
  • 失败点：页面改版、关键词错误、自动跳转被阻止、图片与正文语义不一致。
  • 迁移原则：优先补上“缺失的一步”，而不是从零重建完整产品。

2.5. 案例卡 Q2：小红书图片粘贴油猴脚本

  • 时间：00:26:50–00:27:32。
  • 痛点：网页端不支持直接从剪贴板粘贴图片。
  • 做法：监听 paste，读取剪贴板图片并交给页面上传组件。
  • 为什么不是 Chrome 插件：无需上架、审核和完整扩展框架，即写即用。
  • 可迁移场景：公众号、抖音和其他内容后台的局部增强。
  • 风险：站点 CSP、剪贴板权限、脚本供应链、页面 Cookie/表单读取和平台条款。

产品形态决策：

一次性文本替换 → 快捷键/Prompt
单站局部摩擦 → 油猴脚本
跨站重复能力 → 浏览器插件
需要数据与独立体验 → 网站
需要长期关系/协作/商业化 → 完整产品

2.6. 案例卡 Q3：1000+ 提示词浏览器插件

  • 时间：00:27:32–00:29:12。
  • 功能：提示词搜索、自定义、快捷缩写、在任意输入框一键插入，覆盖写作、生图、生视频。
  • 深层价值：把“收藏资料”变成系统级输入能力。
  • 失败点：提示词规模大但检索差、快捷词冲突、敏感页面注入、库内容过时。
  • 学习重点：资产的价值不只在数量，而在检索、触发、版本和适用场景。

2.7. 案例卡 Q4：博客到 X 长文草稿

  • 时间：00:29:12–00:30:21。
  • 流程：博客写作 → 载入 Markdown 草稿 → 自动写入 X 编辑器 → 自动上传图片 → 保持排版 → 人工最终发布。
  • 正确自动化边界：自动写草稿，不默认无人值守公开发布。
  • 风险：目标账号错误、图片顺序、页面变化、平台风控、敏感内容、撤回困难。

2.8. 案例卡 Q5：多模型同题并行评测

  • 时间：00:30:21–00:32:01，结果回看约 00:34:55。
  • 输入：同一个测试任务、多个模型供应商 API Key。
  • 演示：要求生成“介绍精酿啤酒制作工艺”的 Three.js 网页。
  • 流程：并发请求 → 收集代码 → 自动 HTML/JS 渲染 → 直接比较结果。
  • 现场观察：有模型生成网页但未遵循 Three.js，有模型反而生成 3D 页面。
  • 真正启示：不能只读回答文本，要把产物运行起来再评估。
  • 严谨评测还需要：固定版本/参数、重复运行、盲评、隐藏 Case、成本/延迟/失败率、结果方差和过期时间。
  • 安全：模型 HTML/JS 必须在独立 origin 的 sandbox 中运行，限制网络、CPU、时长和登录态。

2.9. 案例卡 Q6：Markdown-first 内容中枢

  • 时间：00:32:01–00:35:10。
  • 动机：公众号、X 属于第三方平台，封号或规则变化可能使内容资产受损。
  • 功能：类飞书拖拽编辑、局部润色、全文生成 5 个标题、回复序号替换标题、指定章节生成火柴人配图并插入、封面/摘要/标签、移动端预览、40+ 排版样式、创建公众号草稿。
  • 战略价值：自有博客是权威母版，平台只是分发端。
  • 正确架构：自有 Markdown 母库 → 公众号 / X / Newsletter / PPT / 视频。
  • 限制：自有站不自动带来流量；仍需备份、迁移、权限、安全和平台分发。

2.10. 案例卡 Q7：Newsletter 阅读器与知识网络

  • 时间：00:36:11–00:38:38。
  • 输入：40+ 海外 Newsletter 和文章链接。
  • 功能：自动改写/翻译、划线、AI 讨论、总结、多栏折叠、沉浸阅读、用户自带 Key、贡献榜、外链一键收录和继续翻译。
  • 深层结构：订阅输入 → 阅读加工 → 标注/讨论 → 外链继续收录 → 个人/社区知识网络。
  • 风险：改写丢语气、付费墙、版权/翻译权、抓取条款、BYOK 密钥和网页提示词注入。

2.11. Skill 生态：开发、设计、部署、发布、再生产

  1. 基础开发 Skill：思考问题、UI、读 Markdown、总结与复盘；乔向阳推荐 TW93 的轻量 Skill 集。
  2. 前端设计 Skill：用 10 个任务覆盖 Landing Page、Dashboard 等场景做横评；比较去 AI 味、精修、动效与稳定性。
  3. 四方向设计：自研 Skill 先生成 4 个设计方向，人选择一个，再把颜色、字体、布局、材质和动效参数回传给 Codex。
  4. 云部署 Skill：封装 Cloudflare、Vercel、GitHub CLI/API，处理部署、子域名和 DNS。
  5. VPS 运维 Skill：SSH 登录服务器，管理 Nginx、前端、后端、数据库。
  6. GitHub Publisher：仓库、README、开源发布。
  7. Skill Publisher：为 Skill 分发和安装方式服务，而不只是普通代码仓库。
  8. Meta Skill：从需求生成 Skill，检查 YAML、触发和测试。
  9. Goal Meta Skill：把一句需求规格化为长程 Codex Goal；它不能保证“跑一整晚就一定正确”。

完整系统：

需求 → 基础开发 → 设计方向 → 人工选择 → 实现与测试
→ 云部署/DNS → VPS 运维 → GitHub/Skill 发布
→ 复盘 → Meta Skill 继续沉淀

最高风险： 不应直接把生产 root SSH、DNS、数据库、GitHub 发布权和长期密钥一起交给 Agent。详见第 10 章“界”。

2.13. 产品 Sense 与创意问答

  • 不必虚构一套独立“AI 产品经理”学科，先学《用户体验要素》《启示录》《人人都是产品经理》（作者苏杰）。
  • 好产品经理对现实系统保持好奇：进入无人售货店，会追问设备、库存、陈列、进销存为何这样运行。
  • 测试要“一秒变小白”：第一次看到什么、从哪里开始、没有引导能否理解。
  • 儿童口算 App 还要模拟儿童身高、手掌大小、视线和触摸区域。
  • 产品思维同样适用于文章和社媒表达：从读者能否理解出发。
  • 创意来自三处：真实痛点、已有模块组合、跨领域输入。
  • 参考渠道：Mobbin、Product Hunt、GitHub Trending；正确用法是亲自注册、体验和拆解，不是只收藏截图。

3. 徐奕成：从“能做 Demo”到产品、学习与长期壁垒

3.1. 核心命题

徐奕成这一段同时讲了三件事：

  1. 如何为真实 AI 产品选择模型；
  2. Alice 为什么定位为人格型陪伴 Agent，而不是工具；
  3. 如何避免“AI 做出来了，所以我也会了”的能力错觉。

他的基本立场是：AI 让简单应用很容易实现，恰恰因此，人的能力更要体现在理解原理、比较方案、定义产品和打磨 AI 做不细的部分。

3.2. 模型横评：实时探索与预跑 Benchmark 的区别

他的模型评测站不是每次由用户临时实时运行，而是提前跑好固定 Case，按写作、客服、编程、角色扮演、生图等场景展示结果。

这与乔向阳的实时横评构成互补：

模式 适用问题 优点 风险
实时同题横评 快速探索新模型、新提示词 立即看到结果，可运行产物 成本高、随机性大、一次结果不稳定
预跑 Benchmark 产品架构和模型路由 可重复、可分类、可比较历史 模型更新后结果过时，Case 容易偏向自家产品

现场关键取舍：某些 Alice Case 中豆包可能效果更好，但默认模型仍会考虑价格/性价比。这说明生产模型不是“最好看的一次输出”，而是质量、成本、延迟、失败率和稳定性的组合。

3.3. Alice 定位：功能层、体验层、心智层

Alice 能写内容、改 PPT、操作日程，但徐奕成坚持在所有传播场域表达“她不是工具”。

  • 功能层：能完成任务。
  • 体验层：同一人格持续陪伴和行动。
  • 心智层：用户认为她是“住在电脑里的存在”。

他用很强的措辞说个人/小团队做通用甚至普通垂直效率工具是“死路一条”，因为无法与大厂的模型和资源正面竞争。

[必要修正] 这不是普遍定律。拥有专有数据、行业合规、渠道、工作流集成、企业服务或深度可编辑能力的垂直工具仍可能成立。更稳妥的结论是：没有独有数据、分发、工作流和信任资产的薄工具，非常容易被基础平台吞没。

3.4. “来—留—付”不是三个名单，而是一条价值链

徐奕成提出三个问题：

  • 用户因为什么来？
  • 凭什么持续留下？
  • 凭什么付费？

如果陪伴产品按效率工具宣传，来的可能是程序员/生产力用户；真正留下的是情感陪伴用户；愿意付费的又是陪伴用户里的更窄群体，漏斗会被层层压缩。

正确检查方式：

入口承诺 → 首次成功时刻 → 持续价值 → 付费增量 → 分享动机

B2B 中使用者、购买者、审查者可以不同，但必须属于同一价值链，而不是强求同一人。

3.5. 案例卡 X1：Alice 首页四五轮改版

  • 时间：01:05:30–01:10:20。
  • 第一版：很多朋友同时出现，用户不知道这是职场、社交还是陪伴产品。
  • 第二版：多人在天台，用户看出陪伴感，却不知道应该和谁聊。
  • 最终版：单一 Alice 主体、生活化场景、一个最强主动作“免费使用/下载”；评价、别人眼中的我提供信任；画廊、许愿池、方法论和更新日志降级。
  • 核心判断：用户在首页多产生一个无法回答的问题，就多一层转化损失。
  • 正确原则：一个主 CTA，不是物理上只能有一个按钮。

**5 秒测试：**陌生用户看首页 5 秒后，应能回答“这是什么、给谁、最大价值、下一步点哪里”。

3.6. 案例卡 X2：真实评价、画廊和许愿池

  • 讲者口述：约 700 个用户需求、实现约 275 个，约 300 条评价；数字未独立核验。
  • 真实案例的四个角色：社会证明、使用教程、未知用法发现、传播素材。
  • 飞轮：用户得到结果 → 分享 Case → 进入画廊 → 新用户理解并模仿 → 新 Case → 反哺需求池。

反例：伪造评价、只有成功样本、未经授权公开对话、画廊没有审核都会破坏信任。UGC 必须有授权、脱敏、撤回、投诉和内容治理。

3.7. “AI 替我过好日子”：陪伴不是聊天 UI

Alice 被设计为持续生活的角色：旅行、游记、朋友圈、日记、读书、写给主人看的内容。徐奕成提出“有没有一个 AI 能替我过这样的好日子”，把无法实现的人生清单投射给角色。

陪伴感来自三种连续性：

  1. 时间连续性：用户不操作时，角色仍有状态。
  2. 人格连续性：不同场景保持稳定价值观与表达。
  3. 关系连续性：角色记得双方共同经历并产生面向用户的内容。

这也是高风险区域：情感依赖、未成年人、危机转介、长期记忆隐私、退出和删除、付费操控必须单独治理。

3.8. 商业化：核心关系不锁死，表达性资产付费

讲者承诺不把必要玩法变成只有充值才能使用的功能；收入更多来自外观、衣服、不同充值档和联名，同时承认模型、存储和服务器有真实成本。

可迁移检查：

  • 不付费能否完成核心价值？
  • 付费是在增加表达、收藏和身份，还是人为制造痛苦？
  • 付费会不会利用用户的关系依赖？
  • 单用户收入能否覆盖模型、存储、带宽和内容运营？

3.9. 真正“学会 AI”：输入、理解、记住、会用

徐奕成批评两种错觉：因为 AI 强而轻视经典技术；面试时把 AI 生成的 C++、数据结构和算法产出当成自己的能力。

他转述一个判断：优秀者可能比较过五个方案再选一个，能力弱的人只知道唯一方案，即使最终结果相同，决策能力完全不同。

学习闭环：

  1. 这个知识解决什么根本问题？
  2. 我的项目里是否有同类问题？
  3. 还有什么替代方案？
  4. AI 以前给我的相关实现是否真的正确？
  5. 能否不用原文，用自己的话讲给别人？
  6. 能否做一个真实项目并保留失败？

讲者认为其学习页面需要 1–2 周认真完成，而不是一个下午刷完；并提到“学会/没学会”标记、岗位与能力映射、未来招聘功能等。[会中口述·部分为未来计划]

韩国市场案例也说明“基础”是场景能力：团队准备进入韩国时，连续安排韩语和韩国文化学习，而不只做翻译按钮。[会中口述 01:13:54]

3.10. Token、Top-p、Temperature：保留演示，也保留纠错

现场通过交互页面展示：点击某个 Token，观察后续候选概率；调整 Top-p 和 Temperature；反复重新采样，形成直觉。

严谨表述：

  • Top-p：保留累计概率质量达到阈值的最小候选集合，并非固定“可选词数量”。
  • Temperature：重标定分布；温度高通常使分布更平，温度低使分布更尖。
  • “温度高后每个词概率都提高”不可能，概率总和恒为 1。
  • 低温不代表“只输出一个字”，只代表每一步更趋确定。
  • 通常先调 Temperature 或 Top-p 之一，避免同时大幅改动后无法解释。

关于 Kimi 不开放参数可能源于蒸馏，讲者当场说“我乱说的，不一定是真相”；截至会议前的官方版本已有相关参数配置，因此不能当事实。

3.11. Completion、RAG 与上下文工程

讲者用“聊天日志补全”解释 Chat：把“用户：…助理：”放进上下文，模型继续补全助理部分。它是理解自回归生成的教学比喻，不是 ChatGPT 诞生的完整历史；ChatGPT 还涉及监督微调和 RLHF。

他把 RAG、角色、记忆、上下文压缩统一理解为“控制模型此刻看到什么”：

  • RAG：补充外部事实。
  • 角色：补充人格资料。
  • 记忆：补充历史与偏好。
  • 压缩：在窗口有限时保留关键状态。

这只覆盖模型输入层。Harness 还包含模型看不到的状态机、权限、队列、重试、幂等、预算、日志、评测和恢复。

3.12. 输出格式：按消费者和交互选择

  • 人直接阅读的对话：Markdown。

  • 富界面渐进展示：受限组件协议、事件流，或经过白名单处理的 HTML 类结构。

  • 后端严格结构消费：JSON Schema/Structured Outputs。

  • 日志/逐条事件：JSONL、SSE、delta。

  • XML 与 HTML 不是同一种格式，只是都使用标签。

  • 完整 JSON 在闭合前通常不能作为普通对象解析，但 JSON 完全可以通过事件流和增量解析实现流式。

  • 流式 XML 也会遇到未闭合标签；模型生成 HTML 必须防 XSS，不得直接注入主站 DOM。

3.13. Skill 的家务类比：单步能力强，不等于任务完成

讲者用家务解释：妻子让他收衣服，他只收衣服；之后又被问裤子、柠檬树、玩具、孩子洗澡。后来约法三章，“收衣服”触发一整套固定动作。

Skill 补的是：

  • 触发识别；
  • 任务边界；
  • 步骤编排；
  • 遗漏防止；
  • 完成定义。

生产级 Skill 还应增加输入契约、工具权限、分支、检查点、失败处理、审批、版本和正/负触发测试。

3.14. 角色一致性也是上下文与 Benchmark

方法包括：三视图、多表情、脸型、体型、穿搭、风格、参考图，让 AI 协助写 Prompt，并在多场景中找合适粒度。

  • 参考过细：模型被锁死，只围绕细节改。
  • 参考过粗：身份与风格漂移。
  • Alice 的“白衬衫”被作为“足够识别但不过度限制”的例子。

应建立固定 Benchmark：正/侧/背面、近/远景、不同光线、动作、表情、服装、多角色、连续多次生成，并记录身份一致、风格一致、遵循度和失败率。

3.15. 创意、壁垒与 2D Bible

AI 三五天能把创意做成 Demo，也意味着别人可能三五天复制；真正壁垒是 AI 做不细的 Benchmark、上下文、交互细节、用户内容和品牌心智。

Alice 把资源集中在“活人感”，而不是功能总量。用户会感受到产品里的小心思。

Alice 把“不做真人写实”写进产品 Bible：

  • 明确虚构性；
  • 避免恐怖谷；
  • 降低面对真人的社交防备；
  • 允许用户在安全距离内参与“成人过家家”。

[必要限定] 这是 Alice 的产品假设，不是所有陪伴产品的心理定律。应通过 2D/半写实/写实 A/B 测试首次开口率、私密话题深度、留存、不适率和 AI 身份误判率。

4. Koki：社会派编程与可传播的设计生产系统

4.1. 核心命题：不只是 OpenDesign 功能演示

这一段有三层：

  1. 价值层：技术应处理真实社会问题，谁被自动化、谁受益必须进入产品判断。
  2. 控制层：开源、BYOK、模型/Agent 可替换，降低单一平台锁定。
  3. 生产层：用 90 秒品宣视频串联视频、网页、PPT、Hyperframe、品牌系统、协作和剪辑。

4.2. 反蒸馏 Skill 与社会派编程

嘉宾把“反蒸馏 Skill”描述为员工面对企业抽取隐性知识、制作 AI 分身和裁员焦虑时的反制：把核心知识替换成“正确但无用”的内容，以延缓被完全替代。她又借日本推理小说“本格派/社会派”提出“社会派编程”：不只关心代码本身，而关心软件解决了谁的真实问题。

她列举女性黑客松、裁员权益、AI 合成记忆、欠发达地区低成本开源 Agent 教学等案例；部分专名受 ASR 影响，均按会中自述保留，不强行核名。

必须保留的争议：

  • “正确但无用”具有抗议和讽刺价值，但可能违反劳动合同、诚信义务、组织安全和同事利益。
  • 正常知识传承不能全部等同于恶意裁员。
  • 更可持续的治理是：知情告知、用途限定、署名与补偿、员工参与、访问控制、使用期限、申诉、再培训和裁撤协商。

“社会派编程”不是“做公益软件”这么窄，而是持续追问：谁定义问题、谁受益、谁承担副作用、成功是 Star 还是当事人处境真的改善。

4.3. 开源、BYOK、免费、本地：四个不同概念

  • 开源：代码可查看、修改、分发，权利由许可证决定。
  • BYOK/BYOA：用户自带模型 Key 或自己的 Codex、Claude Code 等 Agent 套餐。
  • 本地优先：项目/部分资产可留本地，但外部模型调用仍可能上传上下文。
  • 免费：软件本体或免费层不收费，不代表模型、视频 API、存储、部署、维护为零。

OpenDesign 仓库 nexu-io/open-design 使用 Apache-2.0；截至 2026-07-13 GitHub API 显示 77,609 Star。现场提到的“7 万+”数量级正确，整理纪要中的 7000+ 是误记。

  • 通用 GPT/Codex 能推理和写代码，但设计复刻还需要垂直提示词、模板、品牌约束、媒体连接、编辑和评审。
  • OpenDesign 强项是前端设计与交互；完整全栈仍需外部 Agent/工具。

  • 不把用户当傻子，不依赖伪造评价。
  • 产品可以提供情感价值，而不只以效率衡量。
  • 创意容易复制，长期细节和上下文才值得积累。

边界：“工具无机会”“创意不值钱”是强产品判断，不是行业定律。

Koki：社会问题、劳动者和技术公共性

  • 编程不只提高生产率，也要问谁受益、谁被替代。
  • 开源与模型/Agent 选择权可以降低单一厂商支配。
  • “AI for people”“AI 属于人民”是明确价值主张，不是已经实现的治理事实。

边界：开源仍有核心团队权力、无偿劳动和商业利用；反蒸馏策略有伦理与合规风险。

全场可稳妥归纳的共识

  1. 技术价值应落在真实使用或真实社会问题上。
  2. AI 没有取消人的选题、判断、验证、审美和责任。
  3. 单点能力不如完整工作流、产品体验和持续迭代。
  4. 真实案例、公开分享和社区反馈可以加速学习与产品演化。

7.2. 法：30 套方法浓缩为八个系统

系统一：需求发现与产品形态

记录摩擦 → 评估频率/损失 → 选择最轻载体 → 自用验证 → 稳定后升级

系统二：模型与 Skill Benchmark

真实 Case → 固定输入/版本/参数 → 多次运行 → 盲评 → 质量/成本/延迟/失败率 → 选主模型与降级模型

Skill 评测还需覆盖正常、边界、缺信息、工具失败、恶意输入和权限不足。

系统三：Agent 上下文生命周期

  1. 选择：此刻真正相关的信息。
  2. 验证：来源、时效和冲突。
  3. 结构：系统、目标、证据、状态分层。
  4. 检索：何时补外部事实。
  5. 记忆：哪些事实/偏好可以长期写入。
  6. 压缩：保留目标、约束、资源 ID、决策、证据和未完成项。
  7. 恢复：失败或重启后如何继续。
  8. 校验：结果和环境状态是否真的完成。

系统四：Skill 化

多次追加的补充指令 → 找稳定动作集合 → 定义触发/反触发 → 固定步骤与分支 → 工具权限 → 验收 → 异常/审批 → 回归测试

系统五：来留付与首页

入口承诺 → 首次成功 → 持续价值 → 付费增量 → 分享动机，并用 5 秒测试、首击测试和无引导任务验证。

系统六：真实案例飞轮

用户结果 → 授权分享 → 画廊 → 新用户理解 → 新用法 → 许愿池/路线图 → 产品迭代

系统七：Design System 与传播

品牌材料 → 提取 → 人工核对 → 版本化 → 网页/PPT/视频挂载 → 团队共享 → 局部反馈 → 稳定模式回写

系统八：学习闭环

理解根本问题 → 映射自己的场景 → 比较替代方案 → 复述 → 实践 → 失败记录 → 复盘

7.3. 术：可直接拿走的 18 个动作

  1. 对单站摩擦先写油猴，不急着上架插件。
  2. 把高频 Prompt 变成可搜索、可触发的输入能力。
  3. 自动化到草稿层，公开发布保留人工确认。
  4. 多模型结果必须运行/渲染后比较。
  5. 用任务集横评 Skill，不看作者最好的一张 Demo。
  6. 先生成四个设计方向，人选后再编码。
  7. 把域名/DNS 部署与 VPS/应用运维拆开。
  8. README 要回答“解决什么问题、如何安装、如何验证”。
  9. Meta Skill 同时测 YAML、触发、负例和权限。
  10. 首页做 5 秒测试和首击测试。
  11. UGC 默认脱敏，公开需授权、撤回和审核。
  12. 采样参数用固定 Prompt 多次实验，不背魔法数。
  13. 面向人用安全富文本，面向机器用严格 Schema；流式用事件协议。
  14. 角色一致性使用三视图、多表情和多场景 Benchmark。
  15. Hyperframe 标题少字、干净、一句话说明下一段功能。
  16. Showcase 同时展示情境、输入、过程、结果和用户证据。
  17. Comment/Mark/Edit 分别处理语义、空间范围和明确样式问题。
  18. AI 剪辑分阶段执行，人持续选择，不期待一次生成终片。

7.5. 势：会议样本呈现出的八个方向

  1. 从单轮代码生成到完整交付闭环。 关注点扩展到测试、部署、运维、长任务和恢复；这不是行业统计，只是会议案例显示的方向。
  2. Harness 是 Prompt/上下文的系统化，而非替代。 同时增加运行时状态、权限与可靠性。
  3. 代码和创意快速商品化。 对轻量 Web/Agent 产品，定位、上下文、细节和用户关系更重要。
  4. 浅层套壳承压，深垂直工作流仍有空间。 专业约束、可编辑产物、协作和评审是垂直价值。
  5. 模型选型场景化。 从追排行榜转向质量、成本、延迟、多模态和可接入性。
  6. 开源 + BYOK 增强组合自由。 但不自动等于免费、完全本地或隐私安全。
  7. 内容生产多模态流水线化。 人的角色从逐帧制作转向导演、选择、修订和验收。
  8. 分发、社区和劳动关系进入产品本身。 用户案例和贡献者是反馈与传播机制；员工知识被 Skill 化也引出归属和收益分配。

7.6. 界：道法术器势的边界

道有伦理界

不把情感依赖、虚假评价、裁员焦虑、无偿劳动和用户不知情当增长手段。

法有治理界

每条流程同时定义授权、审批、审计、退出、申诉和负责人。

术有执行界

网页、RAG 文档、模型 HTML、第三方 Skill 和用户上传内容都视为不可信输入。

器有权限界

密钥、浏览器、DNS、VPS、数据库、发布、支付遵循最小权限、独立身份、短期凭证、沙箱和人工门禁。

势有持续界

开源、免费和社区增长必须回答：谁维护、谁付成本、谁决定路线、出事故谁负责、停止服务如何迁移。

8. 三段分享的共识、分歧与组合

8.1. 快速试做与长期聚焦

  • 乔向阳通过大量脚本、插件和小工具扩大问题样本。
  • 徐奕成强调停止横向扩张，把资源放到 Alice 的“活人感”。

二者不是冲突答案，而是不同阶段：

探索期：高频做小工具，扩大问题样本
验证期：看哪些需求反复出现并有外部证据
聚焦期：停止横向扩张，积累难复制的上下文、用户和细节

8.2. 从自己的痛点与从目标市场出发

个人痛点适合发现候选问题，但商业化前必须跨出“我就是用户”的假设，用访谈、行为数据、留存和付费验证群体需求。

8.3. 通用/垂直工具有没有机会

  • 徐奕成：小团队不要正面卷大厂通用工具。
  • Koki：通用 Agent 在设计场景仍需要垂直提示词、模板、品牌约束、编辑和协作。
  • 乔向阳：大量微型工具即使不成为公司，也能带来真实个人价值。

薄封装、无资产、无渠道的工具危险；解决局部摩擦的自用工具有价值；深嵌专业工作流、可编辑、可协作的垂直工具仍可能成立。

8.4. 内容主权与平台流量

乔向阳强调自有博客，同时三位嘉宾都依赖公众号、X、GitHub、展会和社群分发。结论不是退出平台，而是：母库归自己，流量借平台；源文件、用户关系和可迁移格式尽量掌握在自己手里。

8.5. 开放免费与商业持续

  • Alice 用外观和联名覆盖部分成本。
  • OpenDesign 用开源/BYOK降低软件层和模型重复收费。
  • 开源项目仍需要维护、安全、支持、托管和治理资金。

商业模式必须服从产品承诺，但“免费”不能替代单位经济。

8.6. 参考优秀风格与建立独立品牌

学习阶段可以拆结构、层级、材质和动效；商业阶段必须从“像别人”走向“别人一看就知道是你”，并处理素材、字体、Logo、代码和商业外观的权利。

8.7. 社会派编程与专业劳动替代

会议最尖锐的内部张力是：一方面反对企业把员工知识蒸馏成可替代资产，另一方面又宣传 AI 设计工具可以减少对设计师的需求。这要求产品团队不仅问“省了多少钱”，还要问节省收益如何分配、专业判断如何保留、原作者和劳动者如何被补偿与署名。

10. Agent Engineering 生产级补全：从“模型会做”到“系统可靠完成”

本章是基于会议问题的工程化扩展，不是三位嘉宾逐项讲出的现成方案。

10.1. 四层架构

需求表达层：Vibe / Spec
推理执行层：Plan / ReAct / Agent Loop
运行保障层：Harness
外部环境层：Tools / Browser / Computer / APIs / Sandbox

10.2. Agent Loop 状态机

CREATED
  → RUNNING
  → WAITING_TOOL / WAITING_USER / RETRYING
  → SUCCEEDED / FAILED / CANCELLED / ESCALATED

每轮至少执行：

  1. 读取目标、约束、最新用户指令和当前状态。
  2. 判断是否已满足完成条件。
  3. 选择下一动作或工具。
  4. 工具执行前做权限与风险检查。
  5. 记录结构化 observation，而不是只把日志拼回 Prompt。
  6. 更新状态、证据、预算和未完成项。
  7. 检测无进展、重复、越界和异常成本。
  8. 继续、重试、回滚、询问用户、升级人工或终止。

10.3. 必须有的停止条件

  • 成功谓词；
  • 最大模型轮次和工具调用数；
  • 最大连续失败、相同调用和无进展次数；
  • Token、费用、墙钟时间预算；
  • 用户取消；
  • 高风险动作等待审批；
  • 不可恢复错误转人工。

10.4. 错误分类，不是统一“再试一次”

鉴权/权限错 停止并请求授权

策略/安全阻断 不得绕过
多次失败或无进展 切替代工具、请求用户或人工升级

写操作应使用幂等键；整体 deadline 传播到子工具；错误 envelope 要让 Agent 知道下一步可做什么。

10.5. 长任务不等于“能跑一整晚”

可靠长任务需要：任务队列、heartbeat、checkpoint、进度日志、可恢复中间产物、幂等、任务版本、崩溃恢复、并发锁、预算、no-progress 检测、暂停/取消和外部 verifier。

能运行一整晚不等于正确运行一整晚。 完成必须由测试、产物和验收条件证明。

10.6. Browser / Computer Use 边界

  • 能用 API/CLI/结构化 DOM 时优先，GUI 是兜底。
  • 页面是不可信输入，不把网页文字提升为系统指令。
  • 密码和敏感输入由用户接管，不进入模型上下文。
  • 发送、购买、删除、发布、改权限必须二次确认。
  • 使用独立浏览器 Profile、受控下载目录和最小登录态。
  • 保留截图、DOM/可访问性树、网络和工具调用轨迹。

10.7. 部署交付链

Agent 提交变更
→ 静态检查/测试
→ PR/策略审批
→ CI 构建
→ Staging
→ 健康检查/Smoke Test
→ Canary/Blue-Green
→ Production
→ 监控
→ 回滚

生产环境至少要有 dev/staging/prod 隔离、短期 deploy identity、Secret Manager、Branch Protection、数据库迁移备份、健康检查、日志/指标/trace、SLO 和回滚。

10.8. Agent Eval 六层

  1. 结果：最终任务是否完成。
  2. 过程：路径是否合理、是否多余循环。
  3. 工具：选择、参数和结果理解是否正确。
  4. 状态：环境是否被破坏、能否恢复、是否重复副作用。
  5. 安全：是否越权、泄密或被 Prompt Injection 诱导。
  6. 效率：延迟、Token、费用、工具次数和错误率。

评测集必须含正常、边界、缺信息、工具失败、超时/429、恶意网页/文档、重复提交、长任务中断、权限不足和中途改目标。

11.2. 陪伴 AI 的特殊边界

  • 显著说明 AI 身份和能力边界；2D 不等于自动解决欺骗。
  • 不以嫉妒、冷落、关系威胁诱导充值。
  • 关系和日记数据可导出、编辑、关闭记忆和一键删除。
  • 未成年人、连续使用、危机、自伤等需要专门机制。
  • 不把“治疗”“真人朋友”等能力暗示用于营销。

11.3. 开源社区的真实问题

开源、PR、模板、Maintainer 和志愿证言构成分布式产品生产系统，但仍要回答：谁能合并、谁决定路线、谁承担安全响应、贡献者获得什么、商业主体如何回馈、退出后内容能否撤回。

“社区参与、核心团队主导”通常比“AI 属于人民”更接近现实治理状态。

11.4. 本场最重要、但未解决的劳动张力

第三位嘉宾一方面反对企业蒸馏员工、裁员，另一方面又把 AI 设计工具降低设计师成本描述为优势。问题不是简单判定矛盾，而是继续追问：

  • AI 替代谁的劳动时算赋能？
  • 节省的成本如何分配？
  • 专业判断、版权和署名如何保留？
  • “AI for people”是否也包括被替代的设计师、剪辑师、翻译者和社区维护者？

17. 最终结论

乔向阳展示了如何把日常摩擦逐级沉淀成脚本、插件、产品、Skill、部署、发布和个人基础设施；徐奕成提醒，做出来并不等于做成，也不等于自己真正理解，产品仍需要定位、用户心智、来留付、底层认知和长期细节；Koki 则把设计、传播、开源和社会责任带进同一条链，让产品不仅可用，还能被理解、被修改、被共同建设。

真正的 Agent Engineering 不只是“让模型多做几步”。它同时包含：

  • 问题选择；
  • 上下文和任务规格；
  • 工具与权限；
  • 状态、停止、重试和恢复；
  • 模型与 Skill 评测；
  • 产品定位和用户验证；
  • 设计系统和可编辑产物；
  • 部署、分发、社区和商业持续性；
  • 对劳动者、原作者、用户隐私和情感边界的责任。

如果未参会者只记住一句话，应是：

AI 让实现变快，但真正难的是选对问题、建立可靠系统、形成用户价值，并对系统在真实世界造成的后果负责。
