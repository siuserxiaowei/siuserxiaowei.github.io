# 02 · pi-ai：用 Models 集合统一模型、错误与用量

版本：Pi v1.5.0 · 核验：2026-11-03T21:19:39+08:00 · 固定源码：`f9a26365568127461c47a07a37dcb42c140a3ac5`

以当前 Models 与 provider factory API 建立模型集合，区分供应商接入、模型操作类型、流式错误和费用来源。

## 先想三个问题

1. Models 集合与某一家 provider factory 各自持有什么？
2. 流返回后的失败，为什么需要同时观察 error 事件和最终消息？
3. usage.cost.total 是供应商账单，还是目录价格估算，如何判断？

## 显式构建 provider 集合

当前推荐从 createModels() 建立集合，再用 setProvider() 注册需要的 factory，例如 openaiProvider()。这比依赖隐式全局注册更容易确定鉴权、模型目录和应用边界。builtinModels() 会显式注册全部内置供应商，方便使用，但也会引入更大的目录与模块入口。

getModels() 和 getModel() 同步读取最后已知的 chat 模型；动态目录获取是显式异步操作。读取模型目录并不证明凭证可用。chat、image、classifier 具有不同操作入口，不能把图像模型对象传给对话 stream。

- 生产应用只接需要的 provider；离线学习可用官方 fauxProvider，不访问真实服务。

## 先统一消息与流，再判断失败

Models 的公开方法接收 Context，并先归一化为 TranscriptContext。供应商实现负责把文本、thinking、工具调用、停止原因和 usage 转换成共同语义。统一接口不能消除模型能力差异，也不能保证换模型后工具表现相同。

流返回后，请求失败通过 error 事件与最终 AssistantMessage 表达，stopReason 为 error 或 aborted；最终消息可以保留部分内容和用量。集合中的鉴权失败会进入流错误，但直接 API 的 streamSimple 在缺少鉴权时可能同步抛错，调用边界仍要做异常处理。

- 先看 stopReason 和 errorMessage，再决定重试；看到部分文本不代表请求成功。

## 用量、费用和重试分开处理

Usage 区分 input、output、cacheRead、cacheWrite 和 totalTokens，并记录相应费用。cost.totalFromProvider 为 true 才表示 total 来自供应商报告的收费；false 或旧记录缺少该字段时，应按目录估算理解，不能当结算账单。

供应商网络失败与执行工具失败属于不同层。模型请求可以按适配器策略做有界重试；工具可能已经发送消息或写入外部系统，不能因为请求重试可行就重复执行。跨模型接续还需要适配历史消息、thinking 与工具格式。


## 实验：用官方 Faux 供应商观察成功与失败

在不使用 API key 的情况下执行两次 pi-ai 请求，核对停止状态和结构化 usage。

运行条件：离线（需预先安装固定版本依赖）

1. 在独立实验目录准备 @earendil-works/pi-ai@1.5.0；以下代码保存为 provider-lab.mjs。
2. 运行 node provider-lab.mjs，保留两次结果。
3. 观察脚本注入的错误如何作为最终消息返回；它不是一次真实供应商故障测评。

```javascript
import assert from "node:assert/strict";
import { createModels, fauxProvider, fauxAssistantMessage } from "@earendil-works/pi-ai";
const faux = fauxProvider();
const models = createModels();
models.setProvider(faux.provider);
faux.setResponses([
  fauxAssistantMessage("hello offline"),
  fauxAssistantMessage("", { stopReason: "error", errorMessage: "injected-error" }),
]);
const context = { messages: [{ role: "user", content: "test", timestamp: Date.now() }] };
const first = await models.complete(faux.getModel(), context);
const second = await models.complete(faux.getModel(), context);
assert.equal(first.stopReason, "stop");
assert.equal(second.stopReason, "error");
assert.match(second.errorMessage, /injected-error/);
assert.equal(typeof first.usage.totalTokens, "number");
console.log({ first: first.stopReason, second: second.stopReason, usage: first.usage });
```

### 预期结果

- first 为 stop，second 为 error，并带 injected-error。
- usage 有数字字段；Faux 的合成 usage 只用于检查结构，不代表真实计费。

验收：断言通过，且没有配置或读取真实供应商凭证；实验验证程序接口，不验证模型质量、成本或重试效果。

需要预先安装固定版本依赖；首次下载依赖需联网。Faux 数据不能拿来推算真实 token 或价格。

## 容易混淆的地方

- 照搬旧全局模型 API，却没有显式注册 provider。
- 只捕获 throw，遗漏流中的 error 与最终 stopReason。
- 把目录读取当鉴权成功，把估算费用当供应商账单。

## 版本变化

示例统一使用 createModels / provider factory，避免把兼容层旧全局 API 当作新应用的默认入口。
