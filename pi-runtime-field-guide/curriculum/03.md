# 03 · 消息与上下文：把历史、执行工具和模型请求分清

版本：Pi v1.5.0 · 核验：2026-11-03T21:19:39+08:00 · 固定源码：`f9a26365568127461c47a07a37dcb42c140a3ac5`

理解 AgentMessage 到模型消息的转换，以及当前 transcript 中的 system sections、工具声明和持久上下文投影。

## 先想三个问题

1. 内部 AgentMessage 为什么可以比供应商消息更丰富？
2. 工具的 execute 函数和发给模型的工具声明是不是同一对象？
3. 修改未来模型上下文时，为什么不应直接抹掉原始历史？

## 应用消息先富化，再收敛

Agent 内部使用 AgentMessage，可以包含标准 system、user、assistant、toolResult，也可以通过 TypeScript 声明合并增加应用角色。默认 convertToLlm 仅保留标准模型角色；自定义通知、UI 状态和审计字段必须由应用明确过滤或转换，不能直接发给供应商。

发送请求前，transformContext 先在应用消息层做裁剪或注入，convertToLlm 再转换为模型消息，最后 normalizeContext 形成只有 messages 的 TranscriptContext。转换应保持工具调用与结果的对应关系，不要为省 token 删掉一半协议记录。

- 工具给模型的 content 与应用使用的 details 各有用途；业务详情不应无选择地进入上下文。

## 系统提示与工具声明属于 transcript

Context 的 systemPrompt 与 tools 是公开入口的简写；归一化后，初始提示、命名 sections 和 toolsAdded 进入首条 system message。后续 system message 可以补充说明、按名称替换或删除 section，并声明 toolsAdded / toolsRemoved。

getCurrentSystemPrompt() 与 getCurrentTools() 按顺序重放这些变更。Agent 的 systemPrompt 是从 transcript 重放得到的只读视图；state.tools 则是本进程可执行的工具集合。它变化后，循环会在下一次请求前把声明差异写入 system message，execute 函数不发送给模型。

- 供应商若不支持中途 system 或工具变化，适配器会按兼容能力折叠消息，不能假定所有模型保留相同缓存前缀。

## 持久会话以投影构造请求

基础 Agent 管当前内存 transcript，CLI 的 AgentSession 则由 SessionManager 生成持久会话上下文。ContextEditEntry 通过追加记录省略或替换早先消息的模型可见内容，原始历史、导出和用量并不会随之删除。

因此，临时 transformContext 与持久 context_edit 不是一回事。前者改变一次请求的输入；后者改变所在分支以后的上下文投影。需要恢复或导航 CLI 会话时，应使用会话管理接口，而不是认为给 agent.state.messages 赋数组就改好了持久历史。


## 实验：离线重放提示 section 与工具移除

验证后续 system 变更只改变当前有效视图，原始消息仍可检查。

运行条件：离线（需预先安装固定版本依赖）

1. 在已准备 pi-ai@1.5.0 的实验目录，将代码保存为 transcript-lab.mjs。
2. 运行 node transcript-lab.mjs；对比重放前的记录和重放后的当前提示、工具。
3. 把第二条 system 的 rules 改成 null 再运行，观察该 section 被删除。

```javascript
import assert from "node:assert/strict";
import { normalizeContext, getCurrentSystemPrompt, getCurrentTools } from "@earendil-works/pi-ai";
const echo = { name: "echo", description: "Echo text", parameters: { type: "object" } };
const messages = [
  { role: "system", content: "BASE", sections: { rules: "SHORT" }, toolsAdded: [echo], timestamp: 1 },
  { role: "user", content: "hi", timestamp: 2 },
  { role: "system", content: "", sections: { rules: "LONG" }, toolsRemoved: [{ name: "echo" }], timestamp: 3 },
];
const context = normalizeContext({ messages });
const prompt = getCurrentSystemPrompt(context.messages);
const tools = getCurrentTools(context.messages);
assert.equal(prompt, "BASE\n\nLONG");
assert.deepEqual(tools, []);
assert.equal(messages[0].sections.rules, "SHORT");
console.log({ prompt, tools, originalRules: messages[0].sections.rules });
```

### 预期结果

- 有效 prompt 为 BASE、空行、LONG；当前工具为空。
- 第一条原始消息仍记录 SHORT，说明重放视图与原始记录有区别。

验收：三条断言通过；能指出当前有效声明、历史声明与工具执行函数之间的边界。

这段实验只重放 pi-ai transcript，不冒充 CLI SessionManager 或 context_edit 的端到端测试。

## 容易混淆的地方

- 在自定义 StreamFn 内继续读取不存在的 context.systemPrompt / context.tools。
- 直接给只读 systemPrompt 赋值，或把 execute 函数塞进供应商工具声明。
- 把一次请求的裁剪当成已持久保存的会话变更。

## 版本变化

当前请求以 transcript 的 system messages 表达提示和工具变化；CLI 持久上下文以 SessionManager 为准。
