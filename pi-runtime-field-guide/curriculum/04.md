# 04 · 新版 Agent Loop：两个队列与明确的请求边界

版本：Pi v1.5.0 · 核验：2026-11-03T21:19:39+08:00 · 固定源码：`f9a26365568127461c47a07a37dcb42c140a3ac5`

用 steering、follow-up、prepareRequest 和 finishTurn 理解 v1.5.0 的调度与停止，而不是用一个 while 黑盒解释所有继续。

## 先想三个问题

1. steering 什么时候进入上下文，为什么不能回滚正在执行的工具？
2. prepareRequest 与 finishTurn 分别位于一轮的哪个位置？
3. finishTurn 返回 continue 时，已有工具或队列触发的请求会不会再多算一次？

## turn 与 run 不是同一层

一个 turn 包含一次供应商响应及其工具结果；一个 run 可以有多个 turn。模型给出工具调用后，工具执行结果回到上下文，循环再请求模型。没有工具调用时，也要检查待处理输入与宿主决策，不能仅看最终文本是否出现。

steering 影响当前工作链，在当前工具批次完成后的正常轮询点进入；follow-up 等当前工作自然停止后再开启后续工作。默认两类队列均逐条取出，也可配置 all。steering 不会撤销已经发生的文件写入或中断正在运行的工具体。

- 已结束工具批次 → steering；没有更多工具或 steering 时 → follow-up。

## 请求前准备和轮次收口

已选中的输入写入上下文后，prepareRequest 在每次供应商请求之前运行，首轮也包括在内。它可以返回 canonical context、model 或 thinkingLevel 的更新；它本身不轮询队列，执行期间到来的 steering 等下一次正常轮询。

assistant 与全部工具结果完成后，finishTurn 在 turn_end 之前运行，决策在 turn_end 之后应用。返回 undefined 保留调度；end 直接结束本次 run，跳过队列；continue 确保还有一次请求。若工具或队列已经触发该请求，就不会额外再加一次。

- 对 error / aborted 响应仍调用 finishTurn，但它们是硬退出，其决策不生效。

## 停止与 settled 是可观察的时序

工具结果可以给 terminate 提示，只有同批全部最终结果都要求终止，循环才跳过自动续推；混合批次继续正常调度。宿主若用 finishTurn 一直无条件返回 continue，会制造无限循环，应定义任务预算或退出条件。

Agent 的事件订阅按注册顺序等待。agent_end 表示循环不再发新事件，但异步订阅还可能做收尾；prompt() 和 waitForIdle() 要等这些工作结束才 settle。此期间 isStreaming 仍为 true，因此界面不能只凭最后一段文本就宣布全部完成。


## 实验：离线验证 steering 先于 follow-up

用三条预设回答观察队列顺序，并计数 prepareRequest 与 finishTurn。

运行条件：离线（需预先安装固定版本依赖）

1. 在实验目录准备 pi-ai@1.5.0 与 pi-agent-core@1.5.0；将代码保存为 loop-lab.mjs。
2. 运行 node loop-lab.mjs，不配置任何供应商密钥。
3. 第二轮实验可让 finishTurn 在首次响应返回 end；观察两个队列没有被自动消费，再恢复代码。

```javascript
import assert from "node:assert/strict";
import { Agent } from "@earendil-works/pi-agent-core";
import { createModels, fauxProvider, fauxAssistantMessage } from "@earendil-works/pi-ai";
const faux = fauxProvider();
const models = createModels();
models.setProvider(faux.provider);
faux.setResponses(["first", "steered", "followed"].map(x => fauxAssistantMessage(x)));
let requests = 0, finishes = 0, queued = false;
const agent = new Agent({
  initialState: { model: faux.getModel() },
  streamFn: models.streamSimple.bind(models),
  prepareRequest: async () => { requests++; },
  finishTurn: async () => { finishes++; },
});
agent.subscribe(event => {
  if (!queued && event.type === "message_end" && event.message.role === "assistant") {
    queued = true;
    agent.steer({ role: "user", content: "STEER", timestamp: 2 });
    agent.followUp({ role: "user", content: "FOLLOW", timestamp: 3 });
  }
});
await agent.prompt("START");
const users = agent.state.messages.filter(x => x.role === "user").map(x => typeof x.content === "string" ? x.content : x.content.filter(b => b.type === "text").map(b => b.text).join(""));
assert.deepEqual(users, ["START", "STEER", "FOLLOW"]);
assert.equal(requests, 3);
assert.equal(finishes, 3);
assert.equal(agent.state.isStreaming, false);
console.log({ users, requests, finishes, idle: !agent.state.isStreaming });
```

### 预期结果

- users 严格依次为 START、STEER、FOLLOW。
- prepareRequest 与 finishTurn 各运行三次，prompt 返回时 idle 为 true。

验收：四条断言通过，能解释每条用户输入被哪个队列选择；Faux 仅验证调度，不测试真实供应商。

使用绑定到 Models 的 streamSimple 作为 StreamFn，接口来自当前官方 Agent README。示例不会执行文件或网络工具。

## 容易混淆的地方

- 把 steering 理解为能抢占并回滚任意工具。
- 在 prepareRequest 中偷偷消费队列，导致调度顺序改变。
- 无条件返回 continue，或把 agent_end 通知当成异步收尾已经结束。

## 版本变化

shouldStopAfterTurn 已移除；新代码用 finishTurn，处理正常与 error / aborted 的调用差异。
