# 07 · 重试与副作用：先判断能不能再做一次

版本：Pi v1.5.0 · 核验：2026-11-03T21:19:39+08:00 · 固定源码：`f9a26365568127461c47a07a37dcb42c140a3ac5`

区分模型请求重试、Agent 轮次恢复与外部工具副作用；用实际重试分类器和幂等设计控制重复执行。

## 先想三个问题

1. 同为 HTTP 429，为什么限流和余额耗尽不能使用相同策略？
2. 工具超时后，为什么不能直接认定外部操作没有成功？
3. Pi Durable 的 replay:safe 能保证外部系统 exactly-once 吗？

## 先分类，再计算退避时间

v1.5.0 的重试判断基于 assistant 的 stopReason 和 errorMessage。正常结果立即返回，aborted 是终态；只有错误且具有瞬时故障特征时才进入有限重试。网络断连、部分服务端错误和短期限流属于候选，账户额度、预算、计费耗尽则优先排除，即使错误文本同时带有 429。

isRetryableAssistantError 是分类器，不负责整个恢复流程。调用者要先识别上下文溢出，再应用重试预算与报告策略。不能见到 timeout 或状态码就无限重复，也不能通过换一个错误字符串掩盖原始失败原因。

- 错误分类需要同时看供应商语义与账户状态，不能只看 HTTP 数字。
- 用户取消与认证、额度问题应让流程可见地停止或等待处理。

## 预算属于哪一层

retryAssistantCall 接收 enabled、maxRetries、baseDelayMs 和可选 maxAgentDelayMs。初次调用不计入 maxRetries；每次重试按指数退避计算，默认单次等待上限为六十秒。调度前、真正重试前和最终结束时可以发送回调，退避等待也会响应 AbortSignal。

provider 适配层的请求重试与 AgentSession 的 assistant 级恢复不是同一个边界。前者处理一次传输，后者可能重新生成一轮回答。叠加时必须知道总尝试次数和等待上限；否则每层都看似有界，用户却仍会经历很长的等待。

- 记录原始错误、尝试编号、最终结果和取消原因。
- 不要把一次重试成功理解成之前的请求没有消耗费用。

## 工具错误先保留不确定性

工具执行可能已经发邮件、提交订单或写入数据库，结果却在返回途中丢失。因此超时代表“结果未知”，不是“操作未发生”。普通 Agent 的工具异常会回流为 isError 结果；是否再次调用应由明确策略决定，不能套用 provider 的网络重试规则。

可写工具应由业务系统记录稳定的操作标识与幂等键。同一业务动作的重试沿用同一个键；先查询既有结果，再决定继续、补偿或请求人工处理。日志要区分未执行、已确认成功、已确认失败和状态未知，不能仅凭进程是否收到返回值记账。


## 持久化恢复仍有外部边界

独立 Pi Durable 会持久化任务意图与检查点，崩溃后只对声明 replay:safe 的工具执行安全重放，其他中断调用会报告给模型处理。这个声明是开发者对操作性质的承诺，不会自动让任意写接口获得幂等能力。

持久化提交、客户端 requestId 去重和外部系统副作用各有边界。给任务去重，不等于银行、邮件服务或发布平台也参与了同一事务。设计恢复策略时，应把业务幂等与可查询结果放在真实副作用所在的系统中，再用重放声明表达已经具备的安全性。


## 实验：离线比较瞬时失败、额度耗尽与取消

使用 v1.5.0 的真实 retryAssistantCall 和分类器，验证有限重试、终态和等待上限；不访问任何模型服务。

运行条件：离线（需预先安装固定版本依赖）

1. 在含 @earendil-works/pi-ai@1.5.0 的临时 Node 项目保存 retry-probe.mjs。依赖未安装时先联网准备；执行阶段无需 provider 凭证。
2. 运行 node retry-probe.mjs；生产等待被替换为零延迟，produce 返回本地构造的 assistant 消息。
3. 核对瞬时错误的调用次数与额度错误、取消的调用次数，避免把本地 mock 解释成真实供应商可用性测试。

```javascript
import assert from 'node:assert/strict';
import { isRetryableAssistantError, retryAssistantCall, retryDelayMs } from '@earendil-works/pi-ai';
const usage = { input: 0, output: 0, cacheRead: 0, cacheWrite: 0,
  totalTokens: 0, cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0, total: 0 } };
const message = (stopReason, errorMessage) => ({ role: 'assistant', content: [],
  api: 'faux', provider: 'faux', model: 'faux-1', usage, stopReason,
  ...(errorMessage ? { errorMessage } : {}), timestamp: 0 });
const policy = { enabled: true, maxRetries: 2, baseDelayMs: 0 };
let transientCalls = 0;
const result = await retryAssistantCall(async () => {
  transientCalls++;
  return transientCalls === 1 ? message('error', '503 service unavailable') : message('stop');
}, policy, undefined);
let quotaCalls = 0;
await retryAssistantCall(async () => {
  quotaCalls++;
  return message('error', '429 insufficient_quota');
}, policy, undefined);
let abortedCalls = 0;
await retryAssistantCall(async () => {
  abortedCalls++;
  return message('aborted');
}, policy, undefined);
assert.equal(isRetryableAssistantError(message('error', '429 insufficient_quota')), false);
assert.equal(result.stopReason, 'stop');
assert.deepEqual([transientCalls, quotaCalls, abortedCalls], [2, 1, 1]);
assert.equal(retryDelayMs({ baseDelayMs: 1000, maxAgentDelayMs: 2500 }, 5), 2500);
console.log(JSON.stringify({ transientCalls, quotaCalls, abortedCalls, cappedDelayMs: 2500 }));

```

### 预期结果

- 瞬时 503 先失败后成功，共调用两次；额度耗尽和 aborted 各只调用一次。
- 第五次计算出的退避时间受 2500ms 的自设上限限制。

验收：assert 全部通过、退出码 0；把 maxRetries 改为 0 后，瞬时错误也不应再调用第二次。

这是重试策略的本地探针，不执行邮件、支付、部署或模型调用，也不证明外部写操作具有幂等性。

## 容易混淆的地方

- 将 429 一律归为可重试，持续重试余额或订阅额度耗尽。
- 工具已发生副作用却因未收到结果而生成新的业务幂等键。
- 把 replay:safe 当作框架提供的外部事务保证。

## 版本变化

重试按当前公开策略与独立 Pi Durable 的边界讲解，不再将 8 月 core 中的实验性 AgentHarness 当作当前恢复实现。
