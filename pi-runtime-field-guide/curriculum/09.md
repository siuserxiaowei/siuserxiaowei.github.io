# 09 · 上下文预算：历史保存与模型可见内容分开管理

版本：Pi v1.5.0 · 核验：2026-11-03T21:19:39+08:00 · 固定源码：`f9a26365568127461c47a07a37dcb42c140a3ac5`

从 SessionManager 的规范投影出发，使用 ContextEditEntry 改变后续模型输入，同时保留原始历史与用量记录。

## 先想三个问题

1. 为什么修改 agent.state.messages 不能可靠替换 Coding Agent 的持久上下文？
2. ContextEditEntry 的 replacement:null 会删除原始记录吗？
3. 上下文溢出恢复为什么要先保存失败尝试，再修复投影？

## 预算计算针对模型真正会看到的内容

上下文预算不仅是历史消息长度，还包括系统提示、工具声明、新输入、工具结果、预留输出和安全余量。v1.5.0 在每次请求前使用 SessionManager 构造规范投影；已压缩或省略的原始记录仍可保存，但不会继续占据同一份模型输入预算。

系统提示和工具加载变化也会以 system 消息记录。重放这些变更后得到当前提示与工具集合，压缩时还会保存完整系统检查点。因此要分清原始 entry、当前分支、投影消息和最终 provider 请求，而不是把一份数组当作所有层的唯一真相。


## ContextEditEntry 追加修改，不覆盖历史

context_edit 指向当前分支上一条已经产生模型内容的记录。replacement:null 省略该记录；非空 replacement 只替换 content，不改角色、模型、时间或用量等原始元数据。user、assistant、toolResult 和 custom_message 都可成为目标，元数据项和任意跨分支记录不能当作可编辑目标。

同一个目标出现多个编辑时，活动分支上最后的编辑生效。导航回编辑之前，原始内容重新参与上下文；这让摘要、脱敏和失败清理能保持分支语义。原记录仍可被 UI、导出、历史查询和会话账务读取，不能把省略操作当成数据删除或隐私擦除。

- assistant 和 toolResult 的字符串替换会规范成文本块数组。
- 自定义状态用 custom entry；需要模型读取的信息才进入 custom_message。

## 规范上下文由会话管理器重建

buildContextEntries 沿活动 leaf 回到根并处理压缩边界；buildSessionProjection 再应用 context_edit；buildSessionContext 生成交给模型的消息列表。这条链决定 finalized context，不能靠直接赋值 session.agent.state.messages 来持久替换它，下一次规范重建可能覆盖临时改动。

SDK 恢复外部历史时，应提供已含对应 entries 的 SessionManager。临时应用消息可以通过 Agent 的 transformContext 和 convertToLlm 分层处理，但这不等于已经写入会话；任何长期有效的变化都要有可重放来源。


## 溢出恢复也要保留证据

CLI 在新用户输入前以及工具结果完成、准备下一次响应时检查规范上下文。provider 拒绝过长请求或部分 length 终止可触发一次压缩恢复；带工具调用的 length 响应还要保留合成失败工具结果并遵守原有调度，不能粗暴丢弃整个轮次。

失败尝试先成为真实历史，并经过 turn_end、agent_end，再追加 context_edit 修复未来输入，成功压缩后才开始新的重试运行。压缩失败或取消时保留省略编辑，不写成功 compaction，也不安排内部恢复重试。这样错误可审计，后续模型又不会不断读到同一份失败现场。


## 实验：在内存会话中替换、省略，再回到编辑之前

验证 ContextEditEntry 的投影语义和原始历史保留，完全不调用模型。

运行条件：离线（需预先安装固定版本依赖）

1. 准备含 @earendil-works/pi-coding-agent@1.5.0 的临时 Node 项目，保存 context-edit.mjs；使用已就绪依赖后可离线执行。
2. 运行 node context-edit.mjs，依次观察原文、替换文本、省略后的空消息列表及回到原 leaf 的状态。
3. 原文使用实验哨兵，不放真实敏感数据；本节只验证内存投影，不做隐私删除承诺。

```javascript
import assert from 'node:assert/strict';
import { SessionManager } from '@earendil-works/pi-coding-agent';
const manager = SessionManager.inMemory();
const original = 'RAW_CONTEXT_SENTINEL';
const id = manager.appendMessage({ role: 'user', content: original, timestamp: 0 });
manager.appendContextEdit(id, { content: 'short replacement' });
assert.equal(manager.getEntry(id).message.content, original);
assert.equal(manager.buildSessionContext().messages[0].content, 'short replacement');
manager.appendContextEdit(id, null);
assert.equal(manager.buildSessionContext().messages.length, 0);
assert.equal(manager.getEntry(id).message.content, original);
manager.branch(id);
assert.equal(manager.buildSessionContext().messages[0].content, original);
assert.equal(manager.getEntries().filter(e => e.type === 'context_edit').length, 2);
console.log(JSON.stringify({ rawPreserved: true, replacementApplied: true,
  omissionApplied: true, beforeEditRestored: true }));

```

### 预期结果

- 替换后，原始 entry 的内容仍为哨兵文本，模型投影为 short replacement。
- 省略后投影没有该消息；切回原始 entry 时哨兵文本重新出现，两个 context_edit 仍留在原始 entries 中。

验收：四个状态的断言全部通过；不要仅检查 TUI 文本是否变化。

需已安装固定版 Coding Agent 包；首次准备依赖可能联网。SessionManager.inMemory 不创建会话文件，实验不发起 provider 请求。

## 容易混淆的地方

- 把从模型输入省略等同于从文件、导出或账务记录永久删除。
- 直接修改 agent.state.messages 后，认为会话恢复也会保留这个修改。
- 按原始历史的总字符数估计当前窗口，忽略压缩、分支和 context_edit 投影。

## 版本变化

用 v1.5.0 的规范会话投影、系统消息检查点与追加式 context_edit 解释预算，不再把修改内存消息数组当作完整上下文管理方案。
