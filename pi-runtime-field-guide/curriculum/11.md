# 11 · 会话树、上下文编辑与 CLI 恢复

版本：Pi v1.5.0 · 核验：2026-11-03T21:19:39+08:00 · 固定源码：`f9a26365568127461c47a07a37dcb42c140a3ac5`

把磁盘原始历史、当前分支和下一次模型上下文分开，才能解释回退、压缩和恢复。Pi v1.5.0 的 ContextEditEntry 改变后续模型投影，不擦除原始记录，也不回滚已经发生的文件或网络副作用。

## 先想三个问题

1. 同一 JSONL 保存多个分支时，为什么不能把所有 message 按时间拼给模型？
2. 把一条工具结果从上下文隐藏后，原文、用量和外部文件分别会怎样？
3. Multica 记录了 Pi 会话标识，为什么换一台 runtime 仍可能无法续接？

## 一份文件保存历史，一条路径组成当前现场

CLI 默认把会话放在 `~/.pi/agent/sessions/--<path>--/`。表头记录版本、会话 ID 与 cwd；其余条目用 `id/parentId` 连接。当前 leaf 到根的路径决定活动分支；切换 leaf 后追加，形成另一条路径，旧条目继续保留。表头的会话 ID 不是树节点的 ID。

`/tree` 在当前文件内导航；`/fork`、`/clone` 可创建关联的新会话。恢复是按记录重建上下文，不是重新执行过去每个 bash。修改代码后的分支切换不会自动把工作目录恢复到旧版本，文件回滚应由 Git 或快照单独完成。

- 区分：全量原始条目、active branch、模型可见 messages。
- `custom`、`usage`、`context_edit` 不各自产生一条普通模型消息。

## ContextEditEntry 是追加的投影变更

`appendContextEdit(targetId, {content: ...})` 给当前分支上的可编辑消息追加替换；传 `null` 则使目标不参与未来上下文。可编辑目标包括 user、assistant、toolResult 和 custom_message。连续修改同一目标时，当前活动路径上最后一次生效。

`buildSessionProjection()` 把编辑应用到消息内容；目标的角色、来源和账务元数据保留。回到编辑之前的分支，原内容重新参与上下文。压缩另由 CompactionEntry 的摘要、系统检查点和 `firstKeptEntryId` 控制，不能把编辑理解为截断整个日志。

- 原始文件、UI、导出和会话计费保留原记录；隐藏上下文不等于脱敏删除。
- 编辑必须指向活动分支上的上下文消息，不能任意修改另一分支或 usage 条目。

## 恢复要核对路径、进程和真实副作用

`pi --continue` 继续当前目录最近会话；`pi --resume` 打开选择器；`pi --session <path|id>` 打开指定会话，恢复到其记录的 cwd。`--session-dir` 覆盖查找和存储位置，`--no-session` 则仅在内存中保存。迁移电脑时，只有会话标识还不够，文件、原 cwd 和所需工具也必须可访问。

先检查会话文件与工作目录，再检查 provider 配置与凭证，最后验证真实产物。对发送消息、收费、远端写入等动作，恢复前核对外部结果；CLI JSONL 会话不能提供这些动作的 exactly-once 保证。

- SDK 内存实验验证投影和分支；磁盘续接要另在临时项目检查。
- 不要把 CLI 的 SessionManager 与第 12 章独立 Durable 存储 API 混用。

## 实验：不调用模型，验证编辑只影响活动分支

用 v1.5.0 的真实 SessionManager API 同时观察原历史、编辑后的上下文、编辑前的分支。

运行条件：离线（需预先安装固定版本依赖）

1. 在独立实验目录预先准备 `@earendil-works/pi-coding-agent@1.5.0` 依赖，Node 至少 22.19；本实验不需要模型凭证。
2. 把代码保存为 `session-projection.mjs`，执行 `node session-projection.mjs`。

```javascript
import assert from "node:assert/strict";
import { SessionManager } from "@earendil-works/pi-coding-agent";

const session = SessionManager.inMemory();
const original = "原记录 A";
const first = session.appendMessage({ role: "user", content: original, timestamp: Date.now() });
session.appendMessage({ role: "user", content: "另一条消息", timestamp: Date.now() });
session.appendContextEdit(first, { content: "未来模型只见 B" });
const editedLeaf = session.getLeafId();
assert.equal(session.buildSessionContext().messages[0].content, "未来模型只见 B");
assert.equal(session.getEntries().find((entry) => entry.id === first).message.content, original);

session.branch(first);
session.appendMessage({ role: "user", content: "从编辑之前分叉", timestamp: Date.now() });
assert.equal(session.buildSessionContext().messages[0].content, original);
session.branch(editedLeaf);
assert.equal(session.buildSessionContext().messages[0].content, "未来模型只见 B");
console.log("PASS: raw history preserved; context edits are branch-relative");
```

### 预期结果

- 断言全部通过，输出 PASS。
- 全量条目中的第一条仍是“原记录 A”，编辑后的模型上下文为 B。
- 回到编辑前分支时可见 A；返回编辑后的 leaf 时再次可见 B。

验收：比较 `getEntries()` 与 `buildSessionContext()` 的输出；内存实验不证明磁盘耐久性，也不验证外部副作用恢复。

本轮已在 Node 22.23.2 与预装 v1.5.0 SDK 中离线实跑通过；不需要模型凭证。不要拿真实密钥测试“隐藏后是否还在原日志”。 可选扩展（需要真实模型凭证，未计入本章离线通过）：另用已登录的 CLI 在临时目录创建一条会话，退出后用 `pi --session <实际JSONL路径>` 续接，并检查恢复的 cwd；这一步会发模型请求。

## 容易混淆的地方

- 把 context_edit 当成原始记录删除，误以为分享会话已无敏感信息。
- 只改 leaf 就期待已经写入的代码或数据库跟着回滚。
- 跨机器只复制 session ID，却缺失 JSONL、cwd 或 provider 配置。

## 版本变化

8 月关于 JSONL 树的基本判断仍成立；本章补入 v1.5.0 的分支相对 context_edit、系统检查点和当前恢复参数。旧会话继续由 CLI 迁移，不应把其文件直接交给 pi-durable。
