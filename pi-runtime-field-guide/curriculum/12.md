# 12 · 独立 Pi Durable：任务检查点、存储与崩溃恢复

版本：Pi v1.5.0 · 核验：2026-11-03T21:19:39+08:00 · 固定源码：`f9a26365568127461c47a07a37dcb42c140a3ac5`

v1.5.0 的持久任务路线在独立的 @earendil-works/pi-durable。它把对话、任务状态与应用文档提交到存储；API 仍标 Experimental，默认终端 CLI 没有自动换用这套引擎。

## 先想三个问题

1. 一个工具在“外部动作成功、结果尚未提交”之间崩溃，为什么仍需要幂等键？
2. MemoryStorage、SQLite 和 JSONL 分别能保住哪些状态，谁负责单一写入者？
3. 为什么一个 JavaScript Promise 或内存变量不能充当跨进程任务检查点？

## 先分开 Conversation、Task 和 Document

`Harness.open(storage, {models, registry}, context)` 打开持久 Session；`harness.root(context)` 取得同一个根对话。Conversation 保存 transcript；Document 保存类型化 JSON 状态；Task 是有版本、phase 与 checkpoint 的持久状态机。`conversation.commit()` 可把追加条目、文档变更和创建任务放在同一个原子提交。

任务定义由 registry 的扩展提供；存储保存名字与状态，不替你保存程序代码。恢复进程要装回相容任务定义；缺失或不能迁移的定义会阻塞任务。`requestId` 可去重重复输入提交，但不自动去重任务里面的外部写操作。

- `pi.generation` 调模型并拥有其 `pi.tool` 子任务。
- 需要重启后继续使用的数据，应进入 checkpoint、文档或任务结果。

## 恢复从提交点继续，副作用要另作保证

`resume()`、提交输入或等待任务会启动调度。phase 在重启后可能从头执行，所以先保存意图，再执行外部动作，再保存结果；等待时间用 `sleepUntil()` 结束当前 phase，把下一 phase 的 checkpoint 一起持久化。

工具只有声明 `replay: "safe"` 才会在进程中断后重跑；否则给模型 interrupted 错误及已提交输出。即使标为 safe，外部系统仍应使用稳定幂等键。持续崩溃受 restartLimit 约束，不能把自动恢复描述成无限重试或任意步骤只执行一次。

- 任务状态提交与外部邮件、支付、数据库写入不属于同一事务。
- 进度输出可能延迟落盘；默认约 1 秒的未持久窗口，不能声称每个已显示字符都抗崩溃。

## 选择后端，同时定义存储所有权

MemoryStorage 不持久化。SQLite 的 WAL/NORMAL 可承受进程崩溃，但最新提交在断电或宿主故障时仍可能丢失。JSONL 提供追加日志与可选 fsync，且把全量历史留在内存中；长任务通常更适合 SQLite。浏览器还有 IndexedDB，服务端有 Cloudflare Durable Object 适配。

一份 storage 同时由一个进程拥有，库不提供跨进程锁。多个 worker 不应随意打开同一目录抢任务；只读观察者使用 readOnly，不能调用 resume 或写入。实验性版本升级要先备份并在副本演练定义与存储兼容。

- CLI JSONL 会话树与 Durable 的 JSONL 存储不是同一格式。
- 关闭进程与突然崩溃的恢复细节不同，验收时要分别记录故障注入点。

## 实验：保存睡眠检查点，结束进程后重新启动

不用模型和外部副作用，通过真实 JSONL storage 验证任务跨两个 Node 进程恢复。

运行条件：离线（需预先安装固定版本依赖）

1. 在独立 Node 项目准备 `@earendil-works/pi-durable@1.5.0`、`@earendil-works/pi-ai@1.5.0` 与 `@earendil-works/chord@1.5.0`，Node 至少 22.19。
2. 保存为 `durable-recovery.mjs`。用一个全新目录执行 `node durable-recovery.mjs crash ./recovery-lab`；预期以 77 退出，这是实验故障注入。
3. 再执行 `node durable-recovery.mjs resume ./recovery-lab`。保留目录检查证据，不同时启动第二个写入进程。

```javascript
import assert from "node:assert/strict";
import { existsSync } from "node:fs";
import { mkdir, readFile, writeFile } from "node:fs/promises";
import { join, resolve } from "node:path";
import { BACKGROUND_CONTEXT } from "@earendil-works/chord/context";
import { createModels } from "@earendil-works/pi-ai/models";
import { createRegistry, defineExtension, defineTask, Harness } from "@earendil-works/pi-durable";
import { openNodeJsonlStorage } from "@earendil-works/pi-durable/storage/jsonl/node";

const mode = process.argv[2];
if (!["crash", "resume"].includes(mode)) throw new Error("Choose crash or resume");
const directory = resolve(process.argv[3] ?? "./recovery-lab");
await mkdir(directory, { recursive: true });
const idFile = join(directory, "task-id.json");
const context = BACKGROUND_CONTEXT;
const Probe = defineTask({
  name: "lab.recovery", version: 1,
  initial: () => ({ phase: "prepare" }),
  phases: {
    prepare: async (_task, runtime, ctx) => {
      await runtime.sleepUntil(runtime.now() + 1000, { phase: "finish" }, ctx);
      console.log("sleep checkpoint committed");
      if (mode === "crash") process.exit(77);
    },
    finish: (_task, runtime, ctx) => runtime.commit(
      () => ({ status: "terminal", outcome: { status: "completed", result: "recovered" } }), ctx),
  },
  abort: (_task, runtime, ctx) => runtime.commit(
    () => ({ status: "terminal", outcome: { status: "aborted" } }), ctx),
});
const registry = createRegistry();
registry.install(defineExtension({ name: "recovery-lab", tasks: [Probe] }));
const storage = await openNodeJsonlStorage(join(directory, "store"), context, { fsync: true });
const harness = await Harness.open(storage, { models: createModels(), registry }, context);
let id;
if (mode === "crash") {
  if (existsSync(idFile)) throw new Error("Use a fresh experiment directory");
  const root = await harness.root(context);
  id = await root.commit((tx) => tx.createTask(Probe, null, { ownership: { kind: "conversation" } }), context);
  await writeFile(idFile, JSON.stringify(id));
} else {
  id = JSON.parse(await readFile(idFile, "utf8"));
}
const record = await harness.waitForTask(id, context);
assert.equal(record.state.status, "terminal");
assert.equal(record.state.outcome.status, "completed");
assert.equal(record.state.outcome.result, "recovered");
console.log("PASS: same task recovered", id);
await harness.close(context);
```

### 预期结果

- 首次输出 sleep checkpoint committed，进程退出码为 77。
- 第二次以保存的同一 task ID 完成，输出 PASS 与 recovered。
- 未注册任何模型 provider，不产生模型 API 请求；存储与 task-id.json 保留。

验收：记录两次进程退出码、同一 task ID、terminal/completed 结果。它验证已提交 checkpoint 的恢复，不证明外部支付或邮件的 exactly-once。

本轮在 Node 22.23.2 与预装 v1.5.0 依赖中实跑：首次退出 77，第二次恢复同一 task ID 并 completed；没有模型请求。TaskId 按 JSON 保存与读取，保留其原始类型。

## 容易混淆的地方

- 给有外部副作用的工具加 replay:safe，却没有业务幂等键。
- 用 MemoryStorage 做测试后声称断进程仍可恢复。
- 让多个进程同时写同一 storage，或把 readOnly 当可调度副本。
- 把 TaskId 假定为字符串；应保存并恢复原始 ID 类型。
