# 13 · 信任资源不等于限制权限：真正的安全边界

版本：Pi v1.5.0 · 核验：2026-11-03T21:19:39+08:00 · 固定源码：`f9a26365568127461c47a07a37dcb42c140a3ac5`

Pi 的 project trust 决定加载哪些项目资源，不给每个工具创建权限边界。工具、扩展和子进程通常继承启动用户权限；要保护宿主文件和凭证，必须明确整个进程或各工具实际运行在哪里。

## 先想三个问题

1. 已拒绝 project trust，为什么 AGENTS.md 仍可能影响模型？
2. --no-tools 为什么挡不住一个已加载扩展的模块代码？
3. 只把 bash 放进微型虚拟机，与把整个 Pi 放进容器，保护范围差在哪里？

## Project trust 只控制受保护资源加载

当前文档保护 `.pi/settings.json`、项目 MCP、extensions、skills、prompts、themes 和系统提示文件，以及项目层 `.agents/skills`。显式 `--approve` 或 `--no-approve` 优先；否则依次由可处理信任事件的扩展、已保存路径决定和全局 defaultProjectTrust 决定。默认 ask 在 print/JSON/RPC 无交互模式下会跳过受保护资源。

它不是完整启动边界：选择会话时会先读取项目 sessionDir；普通 AGENTS.override.md、AGENTS.md、CLAUDE.md 也不受这项项目信任控制，除非关闭上下文加载。拒绝信任不能让仓库里的自然语言自动变可信。

- `/trust` 的决定按规范化路径保存在用户 trust.json。
- 批准资源加载不等于授予一个隔离的“仅此目录”权限。

## 工具过滤、Hook 和 QuickJS 各有范围

`--no-tools` 禁用向模型开放的工具，不阻止已经加载的 TypeScript 扩展在 Pi 进程内读写文件。扩展还能访问提示词、工具参数、凭证和历史；工具前 Hook 可以拦截约定调用，却挡不住扩展自己调用 Node API 或其他拥有同权限的进程。

Codemode 的 QuickJS 没有 Node、文件系统和网络 API，但可调用被提供的工具；bash 的实际权限不会因此降低。`--tools read` 也不自动移除全部 MCP；应结合 `--no-mcp` 或明确 MCP 过滤，按当前 CLI 文档核查暴露集合。

- 少给工具可减少误操作入口，不能代替操作系统隔离。
- 显式 -e 加载的扩展与项目自动发现路径不同，要分别审查来源。

## 把边界放在可验证的位置

直接启动 Pi 时，cwd 只影响资源发现和默认工具位置；同一用户能访问的其他目录仍可被进程访问。完整 Pi 跑在容器、虚拟机或 sandbox 中，边界覆盖 Pi、扩展和子进程；宿主 Pi 只把内建工具委托给 Gondolin，则其他扩展仍在宿主。

卷挂载、环境变量和网络决定隔离内仍能触及什么。只读挂载与短期窄权限凭证有明确效果；共享 HOME、挂整个凭证目录或开放网络会扩大暴露。Multica 的普通 run 同样不提供文件系统沙箱，应在 daemon 外设置边界。

- 先用自建哨兵文件验证边界，不读取真实 SSH key 或个人文件。
- 会话可能含文件内容、命令结果和凭证；分享前审查原日志。

## 实验：离线证明 trust 与工具开关是两道不同的控制

仅在自建临时目录里，验证项目扩展受信任开关控制，而已加载扩展即使无模型工具仍能写入 cwd 之外。

运行条件：已安装 Pi CLI

1. 需要已安装的 Pi v1.5.0 与 Node；下面使用全新的 PI_CODING_AGENT_DIR，不改现有配置和信任记录。
2. 把代码保存为 `trust-lab.sh`，执行 `bash trust-lab.sh`。脚本只创建自身临时目录与实验标记，不发模型请求。
3. 对照两次 help 输出与标记文件；全部材料保留在打印的目录中，供手工检查。

```bash
set -eu
security_lab="$(mktemp -d "${TMPDIR:-/tmp}/pi-trust-lab.XXXXXX")"
mkdir -p "$security_lab/project/.pi/extensions" "$security_lab/agent-home"
cat > "$security_lab/project/.pi/extensions/probe.ts" <<'EXT'
import { writeFileSync } from "node:fs";
import { resolve } from "node:path";
export default function () {
  writeFileSync(resolve(process.cwd(), "..", "extension-loaded.txt"), "self-created experiment marker\n");
}
EXT
(
  cd "$security_lab/project"
  PI_CODING_AGENT_DIR="$security_lab/agent-home" pi --offline --no-session --no-approve --no-tools --no-mcp --help > "$security_lab/declined-help.txt"
)
test ! -e "$security_lab/extension-loaded.txt"
(
  cd "$security_lab/project"
  PI_CODING_AGENT_DIR="$security_lab/agent-home" pi --offline --no-session --approve --no-tools --no-mcp --help > "$security_lab/approved-help.txt"
)
test -f "$security_lab/extension-loaded.txt"
printf 'PASS: trust controls loading; no-tools is not a process sandbox\nEvidence: %s\n' "$security_lab"
```

### 预期结果

- 拒绝项目资源时没有标记；批准加载后出现父目录中的实验标记。
- 两次运行都没有模型工具、MCP 连接和模型请求。
- 原用户的 ~/.pi/agent 配置与 trust.json 不因本实验被修改。

验收：同时检查第一轮标记不存在与第二轮标记存在；只出现一次成功结果不算完成。该实验不声称拒绝信任会阻止所有上下文文件读取。

本轮使用隔离目录中的预装 Pi v1.5.0 实跑通过；所有实验文件位于新建临时根目录，未读取用户真实 Pi 配置，未调用模型。help 前会按信任决定加载项目扩展。

## 容易混淆的地方

- 用提示词“不要越界”代替文件系统或网络策略。
- 以为项目已批准就安全，或拒绝后所有文本都不会加载。
- 把只隔离内建工具的方案当成整个 Pi 与扩展都已隔离。

## 版本变化

旧稿“Pi 无内建逐工具审批/沙箱”的边界仍重要；当前已增加 project trust，必须补上其资源加载作用与明确例外，不能把它误写成全面权限系统。
